🐳 Docker Fundamentals

Docker is a containerization platform that packages applications and dependencies into lightweight, portable containers.

Key Insight: Containers don't carry an entire OS — they use bare minimum OS and share the host kernel. They start in seconds and consume minimal resources. You can run dozens — even hundreds — on the same machine.

Why Containers?

  • Earlier apps were monolithic → physical servers sufficed
  • Then components split (backend, frontend, DB) → VMs took over
  • Now apps are microservices → containerization tools like Docker serve the purpose
  • Portability problem solved by containerization

🔄 Docker Lifecycle: Build → Ship → Run

Build Create an image (Dockerfile + docker build)

Ship Share via registry (docker push/pull)

Run Start containers (docker run)

Container Runtime

A container runtime is the software responsible for creating, starting, stopping, and managing containers. It turns a container image into a running container.

Types:

  • High-Level: Docker Engine, containerd, CRI-O — handle image pulling, networking, storage
  • Low-Level: runc (OCI-compliant) — directly interact with Linux kernel, namespaces, cgroups
📦 Analogy: Container Image = Packed lunch box | Container Runtime = Person who opens it, serves food, and cleans up

Container States

Created → Running → Paused → Stopped → Deleted

docker create nginx # Created docker start <id> # Running docker pause <id> # Paused docker stop <id> # Stopped docker rm <id> # Deleted

🔒 Namespaces & cgroups — The Core of Containers

Golden Rule: "Namespaces isolate, cgroups control."

🧩 Linux Namespaces (Isolation)

NamespaceWhat It IsolatesExample
PIDProcess treeContainer sees its own PID 1; can't see host processes
NetworkIP addresses, portsMultiple Nginx containers all use port 80 internally
MountFilesystem viewFile changes inside container don't affect host
UTSHostnameEach container can have its own hostname
UserUser/group IDsMap container root → non-root user on host (security)
🚂 Analogy: Namespaces are like separate cabins in a train — same engine (kernel), different passengers, no visibility between cabins.

🎛️ Control Groups / cgroups (Resource Limits)

cgroups limit, control, and monitor resource usage:

  • CPU: Limit usage, assign CPU shares
  • Memory: Set max memory; container is killed if limit exceeded
  • Disk I/O: Limit read/write speeds
  • Network: Indirectly through traffic shaping
⚡ Analogy: cgroups are like electricity meters in apartments — each flat has a limit; one tenant cannot use all power.

📝 Task Discussions (from lecture)

Task 1: Faulty container crashes host (high memory)▼

Q: Which container feature was misconfigured or missing?
→ cgroups (resource limits) were not set.

Q: Which kernel mechanism should have prevented this?
→ cgroups — specifically memory limits.

Q: Would namespaces alone solve this?
→ No. Namespaces only isolate (visibility), they don't limit resource consumption.

Task 2: Three containers — CPU hog, web server, DB▼

Q: Which Linux feature prevents Container A from consuming all CPU?
→ cgroups (CPU limits)

Q: Which feature ensures Container B cannot see processes of Container C?
→ PID Namespace

Q: Which namespace allows all three to use port 80 internally?
→ Network Namespace (each container gets its own network stack)

🏠 Virtualization vs Containerization

Virtualization: Hypervisor partitions physical server → multiple VMs, each with its own full OS. Heavy

Containerization: Containers share the host OS kernel, carrying only app + dependencies. Lightweight

IsolationStrong (hypervisor-level)Process-level (namespaces)
PortabilityLimitedExcellent
Density per Host~10-20 VMs~100s of containers

🏗️ Docker Architecture

Docker uses a client-server architecture with these key components:

ComponentRole
Docker ClientCLI tool (docker command) that communicates with the daemon via REST API

Docker ImagesRead-only blueprints used to create containers

💡 Viva Tip: Docker Client sends commands → Daemon executes them → Images are pulled from Registry → Containers are created from Images.

🖥️ Docker on Windows (Hyper-V)

On Windows, Docker Desktop uses Hyper-V to run Linux containers. Hyper-V creates a lightweight VM that hosts the Linux kernel, and Docker runs containers inside that VM. This is how Windows users get Linux container support!

  • Hyper-V: Microsoft's native hypervisor (Type 1) for running VMs
  • WSL 2: Alternative backend — runs a real Linux kernel inside a lightweight VM
  • Containers still share the same kernel (the one in the Linux VM), not the Windows kernel

📦 Container Images & Registries

A container image is a read-only blueprint containing: Base OS (minimal) + App code + Libraries + Runtime + Config. Images are immutable.

🧅 Image Layers

Each instruction in a Dockerfile = one layer. Layers are immutable, cached, and reused across images.

Base OS Layer → Runtime Layer → Dependencies Layer → Application Code Layer (stacked bottom to top)

✅ Benefits: Faster builds (cache), smaller storage (shared layers), faster deployment (only missing layers downloaded).

🌐 Docker Networking

🔹 Bridge Network (Default)

Default for standalone containers. Containers on same bridge communicate via IP.

docker network ls docker network inspect bridge docker network create my_bridge_net docker run -d --name c1 --network my_bridge_net nginx docker run -d --name c2 --network my_bridge_net alpine sleep 300

🔹 Host Network

Container shares host's networking stack — no separate IP. Linux only.

docker run -d --network host nginx curl http://localhost

🔹 Overlay Network

Used in Docker Swarm for multi-host communication.

docker swarm init docker network create -d overlay my_overlay docker service create --name web --network my_overlay -p 8080:80 nginx

🔹 Built-in DNS

Containers on user-defined bridge networks can resolve each other by container name.

docker network create app_net docker run -d --name backend --network app_net nginx docker run -it --name client --network app_net alpine sh ping backend # ← resolves by container name!

☁️ Microservices & Containers

Microservices Architecture — Breaking a monolithic application into small, independent services that communicate via APIs.

📊 Monolithic vs Microservices

AspectMonolithicMicroservices
StructureSingle codebaseMultiple independent services
DeploymentSingle unitIndependent per service
ScalabilityScale entire appScale individual services
TechnologySingle stackPolyglot (different per service)
Team StructureLarge teamsSmall, cross-functional teams
Fault IsolationPoor (one bug crashes all)Good (isolated failures)

Why Containers for Microservices?

  • Lightweight: Each microservice runs in its own container
  • Isolated: Namespaces provide process isolation
  • Portable: Works across dev, test, prod environments
  • Scalable: Scale individual services independently
  • Versioned: Each service can be versioned independently

Docker Compose for Microservices

Docker Compose lets you define and run multi-container applications using a YAML file.

# docker-compose.yml version: '3' services: web: image: nginx ports: - "8080:80" db: image: mysql:8 environment: MYSQL_ROOT_PASSWORD: root123 app: build: . ports: - "5000:5000" depends_on: - db

⚙️ Maven Build Automation

Maven is a build automation tool for Java projects. It uses a Project Object Model (POM) — an XML file (pom.xml) that describes the project configuration.

Why Build Tools Exist

  • ❌ Manual Compilation Pain: Remembering exact javac commands and classpaths
  • ❌ Dependency Hell: Version conflicts, missing libraries
  • ❌ Inconsistent Builds: "Works on my machine" syndrome
  • ❌ Repetitive Tasks: Testing, packaging, deploying manually

✅ Maven solves all of the above through a standardized, declarative build system.

📁 Standard Directory Structure

my-project/ ├── pom.xml └── src/ ├── main/ │ ├── java/ # Production Java source │ └── resources/ # Config files, properties └── test/ ├── java/ # Test source └── resources/ # Test resources target/ # Generated output

📄 POM (Project Object Model)

<project> <groupId>com.example</groupId> <artifactId>my-app</artifactId> <version>1.0.0-SNAPSHOT</version> <packaging>jar</packaging> <dependencies> <dependency>...</dependency> </dependencies> <build> <plugins>...</plugins> </build> </project>

Key Elements:

  • GroupId: Unique org identifier (e.g., com.example)
  • ArtifactId: Project name (e.g., my-app)
  • Version: Release version (e.g., 1.0.0-SNAPSHOT)
  • Packaging: Output format: jar, war, pom
  • Profiles: Environment-specific configurations (dev, test, prod)

🔄 Build Lifecycle Phases

validate → compile → test → package → verify → install → deploy
PhaseDescription
validateValidate project structure
compileCompile source code
testRun unit tests
packagePackage as JAR/WAR
verifyRun integration tests
installInstall to local repository
deployCopy to remote repository

🧩 Dependency Scopes

Dependency scope controls when and where a dependency is available in the classpath.

ScopeCompileTestRuntimeDescription
compile (default)✔✔✔Available everywhere — compile, test, and runtime
provided✔✔✘Available at compile/test but NOT bundled. Provided by runtime (e.g., Tomcat)
runtime✘✔✔Not needed for compile, but needed at runtime (e.g., JDBC drivers)
test✘✔✘Only for test compilation and execution (e.g., JUnit, Mockito)
system✔✔✘Like provided but references JAR via explicit path (not portable, discouraged)
<dependency> <groupId>junit</groupId> <artifactId>junit</artifactId> <version>4.13.2</version> <scope>test</scope> <!-- Only for testing --> </dependency>

🧩 Parent POM

A Parent POM centralizes configuration across multi-module projects. Child modules automatically inherit all dependency versions, plugin configs, and properties from the parent — following the DRY (Don't Repeat Yourself) principle.

<parent> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-parent</artifactId> <version>3.2.0</version> <relativePath/> </parent> <!-- Child inherits all configs — no need to repeat versions! -->

Benefits: Centralized version management | Shared plugin config | Consistent build behavior | Single place to update versions

🔄 Transitive Dependencies & Version Conflicts

Transitive Dependencies: When you declare A → B, Maven automatically pulls in all of B's dependencies (B → C, C → D ...). You get the full dependency tree without manually declaring each one.

Conflict Resolution — "Nearest Wins": If two paths lead to the same artifact with different versions, Maven picks the version closest to the project root in the dependency tree (shortest path).

Solutions to conflicts:

  • Explicit direct dependency declaration — overrides transitive version
  • <exclusions> to remove unwanted transitive deps
  • <dependencyManagement> to enforce a specific version
<!-- Exclude a transitive dependency --> <dependency> <groupId>com.example</groupId> <artifactId>lib-a</artifactId> <exclusions> <exclusion> <groupId>com.bad</groupId> <artifactId>old-lib</artifactId> </exclusion> </exclusions> </dependency> <!-- Force version via dependencyManagement --> <dependencyManagement> <dependencies> <dependency> <groupId>com.example</groupId> <artifactId>some-lib</artifactId> <version>2.0</version> </dependency> </dependencies> </dependencyManagement>

🔌 Maven Plugins & Execution

Plugins bind goals to lifecycle phases. A goal is a specific task (like compiler:compile or surefire:test). Each plugin has one or more goals.

PluginPurpose
Compiler PluginCompiles Java source code. Controls source/target Java version.
Surefire PluginRuns unit tests. Generates test reports. Skip with -DskipTests.
Shade PluginCreates Uber JAR (fat JAR with all dependencies merged)
JAR PluginPackages into JAR with manifest
dockerfile-maven-pluginBuilds Docker images via Maven

🛠️ Compiler Plugin Configuration

<plugin> <groupId>org.apache.maven.plugins</groupId> <artifactId>maven-compiler-plugin</artifactId> <configuration> <source>17</source> <target>17</target> </configuration> </plugin>

🧪 Surefire Plugin Configuration

<plugin> <artifactId>maven-surefire-plugin</artifactId> <version>3.1.2</version> <configuration> <includes>**/*Test.java</includes> </configuration> </plugin>
💡 Tip: mvn compile triggers compiler:compile goal, mvn test triggers surefire:test goal. Plugins are how Maven actually does everything!

📦 Shade Plugin — Uber JAR

An Uber JAR (fat JAR) contains your compiled code PLUS all dependencies merged inside it. One file, run anywhere.

<plugin> <groupId>org.apache.maven.plugins</groupId> <artifactId>maven-shade-plugin</artifactId> <version>3.5.0</version> <executions> <execution> <phase>package</phase> <goals><goal>shade</goal></goals> <configuration> <transformers> <transformer implementation="ManifestResourceTransformer"> <mainClass>com.App</mainClass> </transformer> </transformers> </configuration> </execution> </executions> </plugin>

📦 Maven Wrapper (mvnw)

Ensures consistent Maven version across environments. Generates mvnw script that auto-downloads the specified Maven version.

# Generate wrapper mvn wrapper:wrapper # Use wrapper (no Maven pre-installation needed) ./mvnw clean package ./mvnw spring-boot:run # Windows mvnw.cmd clean install

🔗 Maven + Docker Integration

Integration Overview:

  1. Build JAR: mvn package produces the JAR in target/
  2. Write Dockerfile: Multi-stage: base image → copy JAR → ENTRYPOINT
  3. Build Image: mvn dockerfile:build
  4. Push to Registry: mvn dockerfile:push

📄 Multi-stage Dockerfile

FROM eclipse-temurin:17-jdk AS build WORKDIR /app COPY . . RUN ./mvnw package -DskipTests FROM eclipse-temurin:17-jre WORKDIR /app COPY --from=build /app/target/*.jar app.jar EXPOSE 8080 ENTRYPOINT ["java","-jar","app.jar"]

<plugin> <groupId>com.spotify</groupId> <artifactId>dockerfile-maven-plugin</artifactId> <version>1.4.13</version> <configuration> <repository>docker-maven-demo</repository> <tag>${project.version}</tag> </configuration> </plugin>

🔄 GitHub Actions — Continuous Integration

GitHub Actions is a CI/CD platform that automates workflows directly inside your GitHub repository.

🤖 Analogy: Think of GitHub Actions like a smart assistant that automatically performs tasks (testing, deployment) whenever something happens in your repository.

Key Components

ComponentDescription
WorkflowAutomated process defined in a YAML file stored in .github/workflows/
JobsSet of steps executed on the same runner. Run in parallel by default.
StepsIndividual commands/actions executed sequentially inside a job
ActionsReusable units of code (e.g., actions/checkout@v4)
RunnersServers that run workflows (GitHub-hosted or self-hosted)
EventsTriggers that start workflows (push, pull_request, schedule)

🔄 Workflow Triggers (Events)

EventDescription
pushWhen code is pushed
pull_requestWhen PR is created/updated/merged
workflow_dispatchManual trigger from GitHub UI
scheduleRuns on cron timing
issuesWhen issue is created/updated
# 1. Push Trigger — runs on push on: push: branches: [main] # 2. Pull Request Trigger — runs on PR on: pull_request: branches: [main] # 3. Schedule Trigger (Cron) — runs at scheduled times on: schedule: - cron: '0 0 * * *' # Every day at midnight # 4. Manual Trigger — run from GitHub UI on: workflow_dispatch:

🔧 Trigger Filters (Branch, Path, Tag)

# Branch-based trigger — only specific branches on: push: branches: [main, dev] # Path-based trigger — only when files in specific paths change on: push: paths: - 'src/**' - '!docs/**' # Exclude docs # Tag-based trigger — runs when a tag is pushed on: push: tags: - 'v1.*' - 'v2.*'

Path filter Only run workflow when code in src/ changes — skip CI for documentation updates! Tag filter Automatically build release artifacts when you push a version tag.

🎯 Event vs Trigger — Key Distinction

From the lecture slides, it's important to understand the difference:

ConceptDefinitionExample
EventThe activity that happens in the repositorypush — code was pushed
TriggerThe condition under which the event runs the workflowbranches: [main] — only on main branch
📌 Formula: Event + Filters = Trigger
"Event = push, Trigger = only on main branch"
# Event alone — runs on ANY push on: push # Event + Trigger filter — runs ONLY on push to main on: push: branches: [main] paths: - 'src/**'

🐳 Docker & Containers (Units 1-2)

Q1: What is a container runtime?
A: A container runtime is software that creates, starts, stops, and manages containers. It turns a container image into a running process. Examples: Docker Engine (high-level), runc (low-level).
Q2: What is the difference between Namespaces and cgroups?
A: Namespaces isolate resources (processes, network, filesystem) — containers can't see each other's resources. cgroups control and limit resource usage (CPU, memory, disk I/O). "Namespaces isolate, cgroups control."
Q3: Name 5 types of namespaces used in containers.
A: PID (process tree), Network (IP/ports), Mount (filesystem), UTS (hostname), User (user/group IDs).
Q4: Why are containers faster than VMs?
A: Containers share the host OS kernel — no guest OS boot needed. They start in seconds vs minutes for VMs, use minimal resources (MBs vs GBs), and can run hundreds on a single host.
Q5: What is port mapping in Docker?
A: Port mapping with -p maps a host port to a container port. Without it, containers are isolated and inaccessible. Example: -p 8080:80 maps host port 8080 to container port 80.
Q6: How do you pass environment variables to a container?
A: Using -e flag (docker run -e MY_VAR=value), --env-file for multiple vars, or ENV in Dockerfile.
Q7: What is the difference between CMD and ENTRYPOINT?
A: CMD provides default command (can be overridden when running container). ENTRYPOINT defines the main executable (harder to override). Often used together: ENTRYPOINT for the command, CMD for default arguments.
Q8: What is an image layer?
A: Each instruction in a Dockerfile creates a layer. Layers are read-only, cached, and reused across images. Benefits: faster builds (cache reuse), smaller storage, faster deployment (only changed layers downloaded).
Q9: What is the difference between Volume and Bind Mount?
A: Volumes are managed by Docker in /var/lib/docker/volumes/, survive container removal, ideal for production data. Bind mounts point to any host directory, great for development (live code reload).
Q10: What Docker network types do you know?
A: Bridge (default, single host), Host (shares host network, Linux only), Overlay (multi-host, Docker Swarm), None (no network), Macvlan (assigns MAC address).

☁️ Microservices (Unit 3)

Q11: What are microservices?
A: Microservices is an architectural style where applications are built as a collection of small, independent services that communicate via APIs. Each service is independently deployable, scalable, and can use different technologies.
Q12: How is monolithic different from microservices?
A: Monolithic = single codebase, single deployment unit, scales entire app. Microservices = multiple independent services, each deployed separately, can scale individual services.
Q13: Why use containers for microservices?
A: Containers provide lightweight isolation (namespaces), portability across environments, independent scaling, versioning per service, and consistent runtime.

⚙️ Maven (Unit 4)

Q14: What is Maven?
A: Maven is a build automation tool for Java projects. It uses a Project Object Model (POM) — an XML file that describes the project configuration, dependencies, and build process.
Q15: List the Maven build lifecycle phases in order.
A: validate → compile → test → package → verify → install → deploy.
Q16: What is an Uber JAR?
A: An Uber (fat) JAR contains your compiled code PLUS all dependency JARs merged inside it. One file, run anywhere with java -jar. Created using the Maven Shade Plugin.
Q17: What is the Maven Wrapper (mvnw)?
A: A script committed to repo that auto-downloads and uses the exact Maven version specified in .mvn/wrapper/maven-wrapper.properties. Ensures consistent builds across environments.
Q18: How do you integrate Docker with Maven?
A: Using the dockerfile-maven-plugin (Spotify). Build JAR with mvn package, then build Docker image with mvn dockerfile:build, push with mvn dockerfile:push.

🔄 GitHub Actions (Unit 5)

Q19: What is GitHub Actions?
A: GitHub Actions is a CI/CD platform that automates workflows inside your GitHub repository. It can build, test, and deploy applications based on events like push, PR, or schedule.
Q20: What are the key components of GitHub Actions?
A: Workflow (YAML file in .github/workflows/), Jobs (parallel tasks), Steps (sequential commands), Actions (reusable units), Runners (execution servers), Events (triggers).
Q21: What trigger types can you use?
A: Push trigger, Pull Request trigger, Schedule trigger (cron), Manual trigger (workflow_dispatch).
Q22: What is Matrix Strategy?
A: Matrix strategy runs the same job with multiple configurations in parallel. Example: test code on Node.js versions 14, 16, 18 simultaneously using strategy: matrix:
Q23: How do you use secrets in GitHub Actions?

Q24: What is a Runner?
A: A runner is a server that executes workflows. Types: GitHub-hosted (Ubuntu, Windows, macOS) or self-hosted (your own server).

🏗️ Jenkins (Unit 6)

Q25: What is Jenkins?
A: Jenkins is an open-source automation server for CI/CD. It follows Master/Agent architecture where the master schedules jobs and agents execute them.
Q26: What is Jenkins Pipeline?
A: A pipeline is a set of automated steps Jenkins follows to build, test, and deploy applications. Defined as code in a Jenkinsfile. Two types: Declarative (structured) and Scripted (flexible, Groovy-based).
Q27: What is the difference between Freestyle and Pipeline jobs?
A: Freestyle uses UI-based configuration, good for simple jobs. Pipeline uses code (Jenkinsfile), version-controlled, supports complex workflows, parallel stages, and conditional logic.
Q28: How do you integrate Docker with Jenkins?
A: Using Docker Pipeline plugin. Define docker.build() and docker.push() in pipeline. Configure Docker Hub credentials in Jenkins. Also possible via shell commands in pipeline steps.
Q29: What are Jenkins Plugins?
A: Plugins extend Jenkins' core functionality. Examples: Git plugin (source control), Docker Pipeline (Docker builds), Maven Integration (Maven builds), HTML Publisher (reports).
Q30: How does Jenkins integrate with GitHub?
A: Through two methods: Poll SCM (Jenkins periodically checks for changes) and Webhooks (GitHub notifies Jenkins on each push — real-time).

➕ Extra Viva Questions (from Course Content)

Q31: What are the 5 components of Docker Architecture?
A: (1) Docker Client — CLI sending commands. (2) Docker Daemon — background service. (3) Docker Images — read-only blueprints. (4) Containers — running instances. (5) Docker Registry — stores/distributes images.
Q32: How does Docker run on Windows?
A: Uses Hyper-V (Microsoft hypervisor) or WSL 2 to create a Linux VM. Docker containers run inside this VM sharing its kernel, allowing Windows users to run Linux containers.
Q33: What is a Path-based trigger in GitHub Actions?
A: Runs workflow only when files in specific paths change. Example: paths: - 'src/**'. Also supports tag-based triggers: tags: - 'v1.*'.
Q34: What are the 5 dependency scopes in Maven?
A: (1) compile — everywhere. (2) provided — compile/test, not bundled. (3) runtime — runtime only. (4) test — testing only. (5) system — explicit path.
Q35: What is a Parent POM?
A: Centralizes config for multi-module projects. Child modules inherit versions, plugins, properties. Spring Boot's spring-boot-starter-parent is a common example.
Q36: How does Maven resolve dependency conflicts?
A: "Nearest Wins" — picks version closest to project root. Fix with: explicit dependency, <exclusions>, or <dependencyManagement>.
Q37: Role of image registry in CI/CD?
A: Bridge between CI and CD. CI builds image & pushes to registry, CD pulls for deployment. Enables build once, deploy everywhere.
Q38: Required Jenkins plugins for Docker?
A: Docker Pipeline, Docker Commons, Git, Maven Integration, Pipeline Stage View, HTML Publisher, SSH Agent.
Q39: What are container states?
A: Created → Running → Paused → Stopped → Deleted. Commands: docker create, start, pause, stop, rm.
Q40: Difference: docker build vs docker run?
A: docker build creates an image from Dockerfile (build time). docker run creates & starts a container from an image (runtime).
