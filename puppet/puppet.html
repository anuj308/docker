1 Configuration Management (CM)

Definition: Configuration Management is the practice of handling changes systematically so that a system maintains its integrity over time.

Analogy Think of CM as a recipe book for servers — it ensures every server is configured exactly the same way, every time. Like a restaurant chain where every outlet must have the same menu, cooking procedures, staff uniforms and table arrangements; CM is the detailed manual guaranteeing consistency across all locations.

In DevOps, CM plays a central role in automating and standardizing environments to enable continuous integration, delivery and deployment. It ensures systems are consistent, scalable and maintainable across development → testing → staging → production.

Key Benefits

Consistency

All servers have identical configurations.

Scalability

Easy to manage hundreds or thousands of servers.

Reliability

Reduces human errors.

Auditability

Track what changes were made and when.

Disaster Recovery

Quick restoration of systems.

Business Impact Example

ScenarioTimeCost (@ $100/hr)
Without CM — 100 servers, 2 hrs each (manual)200 hours$20,000
With CM — automated, all servers0.5 hours$50
Time Saved199.5 hours$19,950

4 Configuration Models: Push vs Pull

These two models describe how configuration changes or updates are applied and distributed across infrastructure.

Push Model Ansible, SaltStack

  • Central control server pushes configurations to target machines/nodes.
  • The control server / CM tool initiates all communication.
  • Target machines are passive recipients (server/client/nodes).

✔ Advantages

Immediate control over updates • Easier to debug (direct command execution) • No agent required (in Ansible).

✘ Disadvantages

Network connectivity issues can block deployments • Less scalable for large infrastructures • Requires direct/open access to targets (e.g. SSH).

Pull Model Puppet, Chef

  • Target machines/nodes periodically pull their configuration or check the central server for updates.
  • The target machines initiate communication.
  • The central server acts as a configuration repository.

✔ Advantages

More scalable for large environments • Nodes self-heal by periodically checking config • More secure (central server needs no SSH access) • Resilient to network issues • Targets work independently • Better security (targets initiate connections).

✘ Disadvantages

Delayed deployment (depends on pull interval) • Less immediate control • Slower to apply urgent changes • Requires agents and proper scheduling.

Practical Comparison

AspectPush ModelPull Model
Deployment SpeedImmediateDelayed (pull interval)
Network RequirementsOutbound from controlInbound to control
ScalabilityLimitedExcellent
SecurityRequires access to targetsTargets initiate connections
Offline TolerancePoorGood
Example Scenario Push: quickly apply a patch to 10 servers → use Ansible to push it instantly.
Pull: keep 1,000 nodes compliant → use Puppet to have them pull and enforce policies every 30 minutes.

5 Introduction to Puppet

Puppet is an open-source configuration management tool that uses a pull-based model to automate the provisioning, configuration and management of servers and applications across your infrastructure.

  • Enables Infrastructure as Code (IaC) by letting you define desired system states using a declarative language.
  • Follows the IaC principle, enabling automation and consistency across servers.
  • Can also be used as a deployment tool — it can automatically deploy software on the system.
  • Because it implements IaC, you can test the environment and ensure it is deployed accurately.

Puppet's Two Main Parts

PartDescription
Puppet Master (Server)Central system that stores configuration (manifests)
Puppet Agent (Client)Installed on every machine you want to configure

6 Key Features of Puppet

1. Declarative Language

Instead of writing scripts that say "how to do something", you write manifests that describe "what you want".

# Instead of scripting:
# 1. Check if Apache is installed
# 2. If not, install Apache
# 3. Start Apache service
# 4. Enable Apache to start on boot

# You simply declare what you want:
package { 'apache2':
  ensure => installed,
}

service { 'apache2':
  ensure => running,
  enable => true,
}

2. Idempotency

Puppet ensures that applying the same configuration multiple times produces the same result without causing issues.

Real-world Example First run: installs Apache, starts service.
Second run: checks Apache is installed and running, does nothing.
Third run: still does nothing (system already in desired state).

3. Cross-Platform Support

Works on Linux, Windows, macOS and various Unix systems.

4. Large Community and Enterprise Support

  • Open-source version available.
  • Enterprise version with additional features.
  • Large community contributions.
  • Extensive module library — Puppet Forge.

Use Cases of Puppet

1. Server Configuration Management

Web server configurations, database server setups, application deployments.

2. Compliance Management

Security hardening, regulatory compliance (SOX, PCI-DSS, HIPAA), audit trail maintenance.

3. Infrastructure as Code

Version-controlled infrastructure, reproducible environments, environment promotion (dev → test → prod).

7 Components of Puppet

Puppet follows a client-server architecture (agent/master model) but also supports standalone mode (puppet apply). Its components can be grouped into core, data and execution layers.

Server-side vs Client-side The Puppet environment breaks into the main server environment and the client environment. On the server side, the Puppet master store holds all configuration files — manifests are the actual code for configuring clients, templates combine code and data to render a final document, files are static content downloadable by clients, modules are a collection of manifests, templates and files, and the Certificate Authority allows the master to sign certificates sent by the client. The Puppet client is the machine that needs to be configured, consisting of Agent and Facter — the agent continuously interacts with the master to ensure certificates are updated appropriately, and Facter collects the client's current state, which is communicated back through the agent.

Detailed Components

ComponentRole / Key Functions
Puppet Master Central server that stores and serves configurations to client machines. Stores manifests and modules • compiles catalogs for agents • manages certificates • serves files and templates.
Puppet Agent (Client) Software running on managed nodes that applies configurations. Requests catalogs from master • applies configurations to local system • reports back to master • gathers system facts.
Manifests Text files written in Puppet's DSL that describe the desired state of system resources.
Modules Reusable collections of manifests, files, templates and other resources organized in a specific directory structure.
Facter System inventory tool that gathers facts about nodes (hardware, OS, network configuration, etc.).
Catalog Compiled document describing the desired state of a particular node, created by the master from manifests and sent to agents.

8 Working of Puppet

Puppet has a master–slave architecture. The complete cycle:

1. Agent sends certificate + ID→ 2. Master signs & returns certs→ 3. Facter sends facts→ 4. Master compiles catalog→ 5. Catalog sent to clients→ 6. Agent applies catalog→ 7. Report sent back→ 8. Repeat at intervals

Step-by-Step Explanation

  1. The client agent sends a certificate with its ID to the server.
  2. The server signs the certificates and sends them back.
  3. Facter collects the state of the clients and sends the facts to the master.
  4. Based on the facts sent, the master compiles the manifests into catalogs.
  5. Catalogs are sent to the clients.
  6. The agent applies the catalog to the local system.
  7. A report is generated by the client describing the changes made and is sent back to the master.
  8. This process is repeated at regular intervals, ensuring all client systems stay up to date.
Puppet Workflow (formal) Agent requests catalog from Puppet Master → Master compiles catalog based on manifests and node classification → Master sends catalog to agent → Agent applies catalog to local system → Agent sends report back to master.
Reference: https://www.puppet.com/docs/puppet/5.5/puppet_index

9 Writing Manifests in Puppet

  • Files written for configuring a node are called manifests.
  • They are compiled into catalogs which are executed at the client.
  • They are written in Ruby with a .pp extension.

12 Puppet Configuration Unit 2

Definition: Puppet configuration refers to the setup and management of system resources and software using Puppet — automating configuring servers, deploying applications and enforcing system policies consistently across multiple machines. It is the act of defining and applying the desired state of systems using manifests, modules and settings, ensuring consistency and automation across many servers.

Prerequisites

  • Puppet installation.
  • Puppet Master status: sudo systemctl status puppetserver
  • Puppet Agent version: puppet --version

What Puppet Does

Puppet lets you define the desired state of your systems — for example:

  • Which packages should be installed (nginx, mysql, etc.)
  • Which services should be running (apache2, docker)
  • Which files should exist and their contents (/etc/hosts, /etc/myapp/config.yml)
  • User accounts and permissions

Once defined, Puppet ensures your systems converge to this desired state automatically.

Key Components of Puppet Configuration

ComponentDescription
ManifestsFiles written in Puppet's DSL, typically with a .pp extension. They describe the desired state of resources.
ModulesCollections of manifests, files, templates and other resources. Allow reusability and organization. Example: a mysql module might include installation, configuration and service management.
NodesDefine which configuration applies to which system (server). Node definitions let you specify different configurations for different servers.
FacterGathers system information (OS, IP, memory) to help make decisions in manifests.
Master & AgentsMaster stores all configurations and modules; agent applies configurations sent by the master. Puppet can also run in masterless mode, where manifests are applied directly on the nodes.

How Puppet Configuration Works

Admin writes manifests/modules→ Agent checks current state→ Compare current vs desired→ Apply changes → compliance

Common Puppet Configuration Files

FilePurpose
puppet.confMain configuration file (locations, logging, master settings)
hiera.yamlHierarchical data lookup (variables and secrets)
auth.confAuthentication & authorization
*.ppManifest files — define the desired state
Module directoriesOrganize reusable code and resources

puppet.conf Sections

Puppet's main configuration file defines how the master and agents behave. It is divided into sections:

  • [main] → Global settings for all Puppet operations.
  • [agent] → Agent-specific settings.
  • [master] → Master-specific settings.
sudo nano /etc/puppetlabs/puppet/puppet.conf
Key Settings certname — unique name of node.
server — Puppet master address.
runinterval — how often the agent checks in.

13 Managing Packages in Puppet

In Puppet, managing packages is a core part of configuration management. Puppet allows you to install, remove or upgrade software packages on your nodes in a declarative way. Declarative syntax ensures idempotency — running the same manifest twice won't break the system.

  • Puppet has built-in resource types like package, service and file.
  • You typically manage packages in manifests — Puppet code files (.pp), usually located in:
    /etc/puppetlabs/code/environments/production/manifests/

Package Resource Syntax

package { 'package_name':
  ensure   => 'installed',   # or 'latest', 'absent', 'purged'
  provider => 'apt',         # optional: apt, yum, dnf, gem
}

Examples

Install a single package:

package { 'vim':
  ensure => installed,
}

Install multiple packages:

package { ['git', 'curl', 'wget']:
  ensure => installed,
}

Combine package + service (with dependency):

package { 'nginx':
  ensure => installed,
}
service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],
}

Run it:

puppet apply nginx.pp

14 Puppet Modules

A Puppet module is a self-contained unit of Puppet code that includes manifests, files, templates and other resources to manage a particular system configuration or application. Modules help you organize and reuse Puppet code by splitting code into several manifests.

One-liner Modules = reusable bundles of Puppet code. They group manifests, files and templates.

Why Use Modules?

Reusability

Write once, use on multiple nodes.

Organization

Keep related configurations together.

Sharing

Puppet Forge allows you to use community modules.

Example use: a module called apache can install Apache, start the service and deploy a website file.

Typical Module Structure

my_module/                # module root folder
├── manifests/            # Puppet code (.pp); init.pp defines the main class
├── files/                # static files to copy to nodes
├── templates/            # ERB templates for dynamic content
└── metadata.json         # describes module (name, author, dependencies)

Puppet 8 Code Directory Layout

/etc/puppetlabs/code/environments/production/
├── manifests/                 # Your main manifests (.pp files)
│   └── site.pp                # Main entry point
└── modules/                   # Your Puppet modules
    └── <module_name>/
        ├── manifests/
        │   └── init.pp
        ├── files/
        └── templates/

Creating the Directories

sudo mkdir -p /etc/puppetlabs/code/environments/production/manifests
sudo mkdir -p /etc/puppetlabs/code/environments/production/modules

# Verify
ls -l /etc/puppetlabs/code/environments

Creating a Module (Puppet 8)

# 1. Generate module skeleton (apache example)
sudo mkdir -p /etc/puppetlabs/code/environments/production/modules/apache/{manifests,files,templates}
cd /etc/puppetlabs/code/environments/production/modules/apache
ls

# 2. If permissions issue:
sudo chown -R $USER:$USER /etc/puppetlabs/code/environments/production/modules

# 3. Generate the .pp file
sudo touch /etc/puppetlabs/code/environments/production/modules/apache/manifests/init.pp

Simple Module Example — Nginx

Add the class in init.pp:

class webserver {
  package { 'nginx':
    ensure => installed
  }
  service { 'nginx':
    ensure => running,
    enable => true
  }
}

Include in site.pp — path: /etc/puppetlabs/code/environments/production/manifests/site.pp

include webserver
Scenario The webserver class ensures Nginx is installed/running across all nodes using the module. A company runs multiple microservices, each needing Nginx — instead of repeating the same manifest, they just include the webserver module.

Full Apache Module (Ubuntu)

class apache {
  # Install Apache package
  package { 'apache2':
    ensure => installed,
  }

  # Ensure service is running
  service { 'apache2':
    ensure  => running,
    enable  => true,
    require => Package['apache2'],
  }

  # Deploy a custom index.html from module files
  file { '/var/www/html/index.html':
    ensure  => file,
    source  => 'puppet:///modules/apache/index.html',
    require => Package['apache2'],
  }
}

Add a static file — path: /etc/puppetlabs/code/environments/production/modules/apache/files/index.html

<h1>Welcome to My Apache Server</h1>

Include the module in site.pp:

node default {
  include apache
}

Apply the module on an agent:

sudo puppet agent -t
Result Puppet contacts the master, compiles the catalog and applies it:
✔ Installs Apache (apache2)   ✔ Starts the service   ✔ Copies index.html

15 Cross-Platform Modules (macOS & Windows)

Module for macOS

class apache_macos {
  # macOS ships Apache (httpd) by default
  service { 'org.apache.http':
    ensure   => running,
    enable   => true,
    provider => launchd,
  }
  file { '/Library/WebServer/Documents/index.html':
    ensure => file,
    source => 'puppet:///modules/apache/index.html',
  }
}

Module for Windows

class apache_windows {
  # Requires Chocolatey to be installed on the Windows agent
  package { 'apache-httpd':
    ensure   => installed,
    provider => chocolatey,
  }
  service { 'Apache2.4':
    ensure  => running,
    enable  => true,
    require => Package['apache-httpd'],
  }
  file { 'C:/Apache24/htdocs/index.html':
    ensure  => file,
    source  => 'puppet:///modules/apache/index.html',
    require => Package['apache-httpd'],
  }
}

Assign the Right Class in site.pp Based on Node Names

node 'ubuntu-agent' {
  include apache
}

node 'macos-agent' {
  include apache_macos
}

node 'windows-agent' {
  include apache_windows
}

A Single File for All Three OSes (Case Statement)

class apache {
  case $facts['os']['family'] {

    'Debian': {
      package { 'apache2': ensure => installed, }
      service { 'apache2':
        ensure  => running,
        enable  => true,
        require => Package['apache2'],
      }
      file { '/var/www/html/index.html':
        ensure  => file,
        source  => 'puppet:///modules/apache/index.html',
        require => Package['apache2'],
      }
    }

    'Darwin': {
      service { 'org.apache.http':
        ensure   => running,
        enable   => true,
        provider => launchd,
      }
      file { '/Library/WebServer/Documents/index.html':
        ensure => file,
        source => 'puppet:///modules/apache/index.html',
      }
    }

    'Windows': {
      package { 'apache-httpd':
        ensure   => installed,
        provider => chocolatey,
      }
      service { 'Apache2.4':
        ensure  => running,
        enable  => true,
        require => Package['apache-httpd'],
      }
      file { 'C:/Apache24/htdocs/index.html':
        ensure  => file,
        source  => 'puppet:///modules/apache/index.html',
        require => Package['apache-httpd'],
      }
    }

    default: {
      fail("Apache is not supported on ${facts['os']['family']}")
    }
  }
}

How This Works

  • Puppet will detect the agent OS automatically using facts['os']['family'].
  • Depending on the OS family it will:
    • Ubuntu/Debian → install apache2, configure /var/www/html/.
    • macOS → enable built-in Apache, configure /Library/WebServer/Documents/.
    • Windows → install Apache via Chocolatey, configure C:/Apache24/htdocs/.
  • You only need to include apache in your node definition (no separate files).

site.pp becomes:

node default {
  include apache
}
Verification When you run the agent: on Ubuntu → applies the Debian block, on macOS → the Darwin block, on Windows → the Windows block. Then open a browser on your Mac and go to http://localhost/ — you should see your Puppet-managed index.html.
