UNIT 1Puppet Basics

What is Configuration Management (CM)? 5 marks

  • Definition: Configuration Management is the practice of handling changes to a system systematically so that the system maintains its integrity over time.
  • It defines and maintains the desired state of every server — same software, same settings, every time.
  • Analogy: Like a recipe book for your servers — it ensures every server is configured exactly the same way, every time. (Restaurant chain: same menu, same procedures, same uniforms, same table arrangement at every branch.)
  • In DevOps, CM plays a central role in automating and standardizing environments to enable continuous integration, delivery and deployment.
  • It keeps systems consistent, scalable and maintainable across development, testing, staging and production.

Key Benefits (write all 5):

BenefitMeaning
ConsistencyAll servers have identical configurations
ScalabilityEasy to manage hundreds or thousands of servers
ReliabilityReduces human errors
AuditabilityTrack what changes were made, and when
Disaster RecoveryQuick restoration of systems
Business impact (optional extra point): E-commerce company with 100 web servers — without CM, manual setup = 2 hrs/server = 200 hrs; with CM, automated = 30 min for all = 0.5 hrs. Time saved ≈ 199.5 hrs ≈ $19,950 (at $100/hr).

What is Puppet? Why do we use it? (Why Puppet) 5 marks

  • Definition: Puppet is an open-source configuration management tool that uses a pull-based model to automate provisioning, configuration and management of servers and applications across infrastructure.
  • It enables Infrastructure as Code (IaC) — you define the desired system state using a declarative language (manifests describe what you want, not how to do it).
  • It can also be used as a deployment tool — it automatically deploys software on systems.
  • Puppet has two main parts: Puppet Master (Server) — central system that stores configuration (manifests); Puppet Agent (Client) — installed on every machine you want to configure.

Why choose Puppet (4 reasons):

  1. Declarative language — write manifests describing the desired end state ("what"), not step-by-step scripts ("how").
  2. Idempotency — applying the same configuration multiple times gives the same result without breaking anything. E.g. 1st run: installs Apache and starts service; 2nd run: checks it is already installed/running, does nothing; 3rd run: still does nothing (system already in desired state).
  3. Cross-platform — works on Linux, Windows, macOS and various Unix systems.
  4. Large community & enterprise support — open-source + enterprise versions, and an extensive module library (Puppet Forge).

Key use cases: (1) Server configuration management (web servers, DB setups, app deployment), (2) Compliance management (security hardening, SOX/PCI-DSS/HIPAA, audit trails), (3) Infrastructure as Code (version-controlled, reproducible environments, dev→test→prod promotion).

Explain the Components of Puppet / Puppet Architecture. 5 marks

Puppet follows a client-server (agent/master) architecture, and also supports standalone mode (puppet apply). Main components:

ComponentExplanation
Puppet Master (Server)Central server that stores and serves configurations to clients. Functions: stores manifests and modules, compiles catalogs for agents, manages certificates (CA), serves files and templates.
Puppet Agent (Client)Software that runs on managed nodes and applies configurations. Functions: requests catalogs from the master, applies configuration locally, sends reports back to the master, gathers system facts.
ManifestsText files written in Puppet's domain-specific language (DSL), extension .pp, that describe the desired state of system resources.
TemplatesCombine code and data to render a final document (e.g. ERB templates for dynamic config files).
FilesStatic content that can be downloaded by the clients (e.g. index.html).
ModulesReusable collections of manifests, templates and files organized in a specific directory structure.
Certificate Authority (CA)Allows the master to sign the certificates (CSRs) sent by clients so secure SSL communication can happen.
FacterSystem inventory tool that gathers facts about nodes (hardware, OS, network, IP, memory). The agent sends these facts to the master.
CatalogA compiled document describing the desired state of a particular node, created by the master from manifests and sent to agents.

Flow in one line: Agent sends facts + requests catalog → Master compiles catalog from manifests/modules → Agent applies catalog → Agent sends report back.

Explain the Puppet Workflow (how Master and Agent work together). 5 marks

  1. Agent requests catalog from the Puppet Master (sending its facts gathered by Facter).
  2. Master compiles the catalog based on manifests, modules and node classification.
  3. Master sends the catalog to the agent.
  4. Agent applies the catalog to the local system (brings node to desired state).
  5. Agent sends a report back to the master.
Diagram to draw in exam:
[Agent] --(1) facts + catalog request --> [Master: manifests/modules/CA]
[Agent] <--(2) compiled catalog (over SSL, port 8140) -- [Master]
[Agent] --(3) applies catalog, sends report --> [Master]

All communication happens over SSL on port 8140, and the master must sign the agent's certificate before an agent can get a catalog.

Short notes: Manifest, Template, Files, Certificate Authority. 5 marks

  • Manifest: The actual code for configuring the clients — files with .pp extension written in Puppet DSL that declare resources (package, service, file, user). Example: site.pp.
  • Template: Combines code and data to render a final document. Used when a config file needs dynamic content (e.g. inserting an IP address or port from facts). Usually ERB templates stored in a module's templates/ folder.
  • Files: Static content that clients download from the master (served via puppet:///modules/… URLs), e.g. index.html for a web server.
  • Certificate Authority (CA): Built into the Puppet Master. When an agent first connects, it sends a certificate signing request (CSR); the CA lists and signs these certificates; only then can the agent communicate securely with the master over SSL. Commands: puppetserver ca list, puppetserver ca sign --certname <name>.

Explain Installation of Puppet (Master on Linux, Agent on Windows/macOS). 5 marks

Important rule: Puppet Master (Server) runs only on Linux (Ubuntu 20.04/22.04, Debian, RHEL/CentOS, Rocky/Alma). Windows and macOS are supported only for the Agent.

A) Install Puppet Master on Ubuntu VM:

# 1. Remove old puppet completely
sudo systemctl stop puppetserver
sudo apt purge -y puppetserver puppet-agent puppet
sudo rm -rf /etc/puppetlabs /opt/puppetlabs /var/log/puppetlabs /var/opt/puppetlabs

# 2. Install Java (required by Puppet Server)
sudo apt install -y openjdk-17-jdk

# 3. Add Puppet 8 repository
wget https://apt.puppet.com/puppet8-release-$(lsb_release -cs).deb
sudo dpkg -i puppet8-release-$(lsb_release -cs).deb
sudo apt update

# 4. Install Puppet Server
sudo apt install -y puppetserver

# 5. Lower Java heap (if VM has less RAM)
sudo sed -i 's/Xms2g/Xms512m/; s/Xmx2g/Xmx512m/' /etc/default/puppetserver

# 6. Set hostname
sudo hostnamectl set-hostname puppetmaster.example.com
echo "127.0.0.1 puppetmaster.example.com puppetmaster" | sudo tee -a /etc/hosts

# 7. Start Puppet Server
sudo systemctl daemon-reload
sudo systemctl enable puppetserver
sudo systemctl start puppetserver
sudo systemctl status puppetserver

B) Install Agent on Windows: download puppet-agent-x64-latest.msi from downloads.puppet.com → run installer (default options) → verify with puppet --version. Important paths: config C:\ProgramData\PuppetLabs\puppet\etc\puppet.conf, SSL certs C:\ProgramData\PuppetLabs\puppet\ssl\, binaries C:\Program Files\Puppet Labs\Puppet\bin\.

C) Install Agent on macOS:

brew tap puppetlabs/puppet
brew install --cask puppetlabs/puppet/puppet-agent
export PATH=/opt/puppetlabs/bin:$PATH
puppet --version
Key directives of puppet.conf (with analogy):
• server=puppet — hostname of the master the agent talks to — "call this number (boss) for work instructions."
• autoflush=true — flush logs/reports to disk immediately — "write down what I'm doing instantly, no waiting."
• manage_internal_file_permissions=false — don't enforce permissions on internal files like SSL certs (useful on Windows) — "don't touch file locks, the OS handles it."
If asked why the agent cannot connect on Windows: Puppet Server is not supported natively on Windows — nothing listens on port 8140 because the Master only runs on Linux. Recommended setup: Master on Linux + Agent on Windows.

Short note: Puppet Development in Isolation. 5 marks

  • Developing/testing Puppet code without touching real production servers — in a safe, separate environment (VM, container, or a separate Puppet environment).
  • Typical isolation environments: a local VM (VirtualBox/UTM) running Ubuntu, a Docker container running puppet/puppetserver and puppet/puppet-agent, or the learning VMs.
  • In isolation you can create modules/manifests, run puppet apply locally, and validate syntax with puppet parser validate before code is promoted to the master.
  • Benefits: mistakes don't break real servers; reproducible test environment; code can be version-controlled in Git and promoted dev → test → prod.
  • Puppet also supports masterless mode (puppet apply) — manifests are applied directly on the node without a master, which is also a form of isolated development.

UNIT 2Advanced Puppet

What is Puppet Configuration? Explain its key components. 5 marks

  • Definition: Puppet configuration is the act of defining and applying the desired state of systems using Puppet manifests, modules and settings, ensuring consistency and automation across many servers.
  • It automates configuring servers, deploying applications and enforcing system policies across multiple machines consistently.

What Puppet defines (examples of desired state): which packages should be installed (nginx, mysql), which services should be running (apache2, docker), which files should exist and their contents (/etc/hosts, config.yml), user accounts and permissions. Once defined, systems converge to the desired state automatically.

Key components:

  • Manifests — files in Puppet DSL with .pp extension describing desired state of resources.
  • Modules — collections of manifests, files, templates for reusability (e.g. a mysql module = install + config + service).
  • Nodes — node definitions decide which configuration applies to which server (different config for different servers).
  • Facter — gathers system info (OS, IP, memory) used to make decisions in manifests.
  • Master & Agents — classic architecture; master stores configs/modules, agent applies them. Puppet can also run masterless — manifests applied directly on nodes.

How it works: (1) Admin writes manifests/modules defining desired state → (2) agent checks current system state → (3) Puppet compares current vs desired → (4) applies changes to bring the system into compliance.

How do you manage packages in Puppet? Explain the package resource. 5 marks

  • Managing packages is a core part of configuration management — Puppet installs, removes or upgrades software on nodes in a declarative way.
  • Declarative syntax ensures idempotency — running the same manifest twice won't break the system.
  • Puppet has built-in resource types: package, service, file (also user, exec…).
  • Manifests usually live in /etc/puppetlabs/code/environments/production/manifests/.

Syntax of package resource:

package { 'package_name':
  ensure   => 'installed',   # or 'latest', 'absent', 'purged'
  provider => 'apt',         # optional: apt, yum, dnf, gem
}

Example — install a package:

package { 'vim':
  ensure => installed,
}

Example — install multiple packages:

package { ['git', 'curl', 'wget']:
  ensure => installed,
}

Full example — package + service (nginx):

package { 'nginx':
  ensure => installed,
}
service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],
}

Run it (masterless/standalone) with: puppet apply nginx.pp

ensure values meaning: installed = just install; latest = install + always upgrade to newest; absent = remove package; purged = remove package + config files.

What are Puppet Modules? Explain the module structure and how to create one. 5 marks

  • Definition: A Puppet module is a self-contained unit of Puppet code that includes manifests, files, templates and other resources to manage a particular system configuration or application.
  • Modules help organize and reuse code by splitting it into several manifests. Modules = reusable bundles of Puppet code.

Why use modules (3 reasons): Reusability (write once, use on multiple nodes), Organization (related configs stay together), Sharing (Puppet Forge community modules).

Module structure:

Folder / fileContains
manifests/Puppet code (.pp). init.pp defines the main class.
files/Static files copied to nodes (e.g. index.html)
templates/ERB templates for dynamic content
metadata.jsonDescribes the module — name, author, dependencies

Creating a module in Puppet 8 (example: apache):

# 1. Create skeleton
sudo mkdir -p /etc/puppetlabs/code/environments/production/modules/apache/{manifests,files,templates}
cd /etc/puppetlabs/code/environments/production/modules/apache

# (if permission issue)
sudo chown -R $USER:$USER /etc/puppetlabs/code/environments/production/modules

# 2. Create init.pp
sudo touch manifests/init.pp

3. Add the main class in init.pp (Ubuntu):

class apache {
  package { 'apache2':
    ensure => installed,
  }
  service { 'apache2':
    ensure  => running,
    enable  => true,
    require => Package['apache2'],
  }
  file { '/var/www/html/index.html':
    ensure  => file,
    source  => 'puppet:///modules/apache/index.html',
    require => Package['apache2'],
  }
}

4. Add static file modules/apache/files/index.html → <h1>Welcome to My Apache Server</h1>

5. Include in site.pp (/etc/puppetlabs/code/environments/production/manifests/site.pp):

node default {
  include apache
}

6. Apply on agent: sudo puppet agent -t → installs apache2, starts service, copies index.html.

Scenario: A company runs multiple microservices; each needs Nginx. Instead of repeating the same manifest, they just include webserver module on every node.

How does one module manage Apache on Ubuntu, macOS and Windows? (case … $facts) 5 marks

One single module can handle all OSes using the case statement on the OS family fact — this is "making configuration dynamic":

class apache {
  case $facts['os']['family'] {
    'Debian': {
      package { 'apache2': ensure => installed }
      service { 'apache2': ensure => running, enable => true,
                require => Package['apache2'] }
      file { '/var/www/html/index.html':
        ensure => file, source => 'puppet:///modules/apache/index.html',
        require => Package['apache2'] }
    }
    'Darwin': {
      service { 'org.apache.httpd': ensure => running, enable => true,
                provider => launchd }
      file { '/Library/WebServer/Documents/index.html':
        ensure => file, source => 'puppet:///modules/apache/index.html' }
    }
    'Windows': {
      package { 'apache-httpd': ensure => installed, provider => chocolatey }
      service { 'Apache2.4': ensure => running, enable => true,
                require => Package['apache-httpd'] }
      file { 'C:/Apache24/htdocs/index.html':
        ensure => file, source => 'puppet:///modules/apache/index.html',
        require => Package['apache-httpd'] }
    }
    default: {
      fail("Apache is not supported on ${facts['os']['family']}")
    }
  }
}

How it works: Puppet detects the agent OS automatically via $facts['os']['family'] → Ubuntu/Debian installs apache2 into /var/www/html; macOS enables built-in Apache via launchd; Windows installs Apache via Chocolatey into C:/Apache24/htdocs. You only need include apache in the node definition — no separate files per OS.

(Alternative: three separate classes apache, apache_macos, apache_windows and node definitions: node 'ubuntu-agent' { include apache } etc.)

Explain Connecting Puppet Agent with Puppet Master (setup + certificate process). 5 marks

This is the most important practical topic. Step summary:

Step 1 — Configure the Master (Ubuntu):

sudo hostnamectl set-hostname puppetmaster.example.com
# /etc/hosts on master:  127.0.0.1 puppetmaster.example.com puppetmaster

# /etc/puppetlabs/puppet/puppet.conf
[main]
certname = puppetmaster.example.com
server = puppetmaster.example.com
environment = production

sudo systemctl enable --now puppetserver
sudo ss -tlnp | grep 8140      # verify master listens on 8140
sudo ufw allow 8140            # open firewall port if ufw enabled

Step 2 — Configure the Agent (any OS):

# /etc/puppetlabs/puppet/puppet.conf   (Windows: C:\ProgramData\PuppetLabs\puppet\etc\puppet.conf)
[main]
certname = agent1.example.com        # unique per node
server = puppetmaster.example.com    # master's address
environment = production
runinterval = 1h

# agent's /etc/hosts — map master name to its IP
192.168.64.5   puppetmaster.example.com puppet

Step 3 — First agent run → sends CSR:

sudo puppet agent --test      # -t = verbose one-time run
# Output: "Creating a new SSL certificate request / fingerprint ..." (waits for signature)

Step 4 — Master signs the certificate:

sudo /opt/puppetlabs/bin/puppetserver ca list
sudo /opt/puppetlabs/bin/puppetserver ca sign --certname agent1.example.com

Step 5 — Run agent again → gets catalog and applies it:

sudo puppet agent --test
Autosigning (optional): create /etc/puppetlabs/puppet/autosign.conf with *.example.com and restart puppetserver — new agents are signed automatically.
Common troubleshooting: connection refused → master not running / port 8140 blocked / wrong server name in puppet.conf or /etc/hosts; SSL errors → clean old certs (sudo rm -rf /etc/puppetlabs/puppet/ssl on agent, re-run); cert mismatch → certname in puppet.conf must match hostname mapping.

Short note: Puppet Classes and Functions (incl. Custom Functions). 5 marks

  • Class: A named block of Puppet code that groups resources (packages, services, files) which together configure one thing, e.g. class apache { … }. Declared/used with include apache. A class can take parameters and is the unit that modules expose — init.pp must contain the class matching the module name.
  • Defined type: like a class but can be declared multiple times with different titles (created with define).
  • Functions: perform actions/return values while the catalog is being compiled, e.g. built-ins: include, require, fail(), template(), lookup().
  • Custom functions: user-written functions in Puppet language saved in a module's functions/ directory (e.g. functions/mymod::greeting.pp) or in Ruby for advanced logic. They extend Puppet beyond built-ins — e.g. a custom function that computes a value from facts.
  • Example of using a function + variable in a manifest: $greeting = "Welcome to ${facts['hostname']}", then file { '/tmp/greet.txt': content => $greeting }.

Explain Using Puppet via Command Line / Managing Resources with puppet apply. 5 marks

  • Masterless mode: with puppet apply a single machine applies a manifest directly — no master needed. Good for testing and one-off configuration.
  • Agents normally run as a service; you can also trigger a run manually with puppet agent -t (test mode: one run, verbose output).

Important commands (write examples):

puppet --version                 # show installed version
sudo puppet apply nginx.pp       # apply a manifest locally (standalone)
sudo puppet agent --test         # one-time agent run against the master
sudo puppet agent -t             # same thing (short form)
puppet config print confdir      # where puppet keeps its config
puppet config print manifest     # default manifests directory
puppet config print modulepath   # where modules are searched
puppet config print server       # which server agent talks to
puppet config set server <ip> --section main   # change master address
puppet config set certname <name> --section main
puppet parser validate file.pp   # check manifest syntax (no output = OK)
puppet resource package vim      # inspect/manage a resource from CLI
sudo /opt/puppetlabs/bin/puppetserver ca list    # list pending certs (master)
sudo /opt/puppetlabs/bin/puppetserver ca sign --certname <name>
puppet apply vs puppet agent: apply = local manifest, no master (masterless); agent = fetches catalog from master using certificates. Both are idempotent.

Short notes: Monitoring Web Servers, Load Balancing Clusters, Scaling Puppet, Making Configuration Dynamic, Extending Puppet, Puppet Manifests. 5 marks

1) Monitoring Web Servers (with Puppet): Puppet can deploy and keep web servers in the desired state — install package (apache2/nginx), keep service ensure => running, enable => true, deploy the site file, and monitor/verify the service; any drift is corrected automatically on the next run.

2) Load Balancing Clusters: Puppet can manage a group (cluster) of identical web servers behind a load balancer — the same module is included on every web node so all have identical configuration, and the load balancer config (e.g. nginx upstream) is managed as another file resource so traffic is distributed across the cluster.

3) Scaling Puppet Environment: as the number of nodes grows: use runinterval to spread agent check-ins, add more compile masters (puppet compilers) behind a load balancer, separate the CA, use autosigning, and organize code into environments (production, development) and modules.

4) Making Configuration Dynamic: use Facter facts in manifests so the same code adapts per node — e.g. case $facts['os']['family'] { … }, content => "Host: ${facts['networking']['ip']}", and templates (ERB) that insert facts into config files. Also runinterval settings, node definitions, and variables.

5) Extending Puppet: add capabilities Puppet doesn't have built-in — custom modules from Puppet Forge, custom functions, custom resource types/providers, and custom facts (via Facter).

6) Puppet Manifests: files with .pp extension containing Puppet DSL code that declares the desired state of resources. Located in /etc/puppetlabs/code/environments/production/manifests/ (e.g. site.pp — entry point that contains node definitions and include statements). Validate before applying: puppet parser validate site.pp.

PRACTICALDay-After-Tomorrow — Do-It-Yourself Steps

Questions will be like: "connect the agent to the master", "do this in a manifest", "create a module", "sign the certificate". Method 1 = Docker (used in class, fastest in exam), Method 2 = VM (Ubuntu master + Windows/macOS agent).

Method 1 — Puppet Master + Agent using Docker (from three.md) know by heart

A. Start the two containers:

docker --version && docker info                    # 1. check docker
docker pull puppet/puppetserver                    # 2. server image
docker pull puppet/puppet-agent                    # 3. agent image
docker run -d --name puppet-server --hostname puppet-server -p 8140:8140 puppet/puppetserver
docker ps                                          # 5. both running?
docker logs puppet-server                          # 6. check server logs
docker run -dit --name puppet-agent --hostname puppet-agent \
  puppet/puppet-agent agent --verbose --no-daemonize --server puppetserver

B. Point the agent at the server IP and run first test:

# 8/9. get IPs
docker inspect -f "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}" puppet-server
docker inspect -f "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}" puppet-agent

docker exec -it puppet-agent bash                  # 10. enter agent
hostname                                           # 11. puppet-agent
puppet --version
puppet config print server
puppet config set server <SERVER_IP> --section main    # 14. e.g. 172.17.0.2
puppet config set certname puppet-agent --section main # 15. set cert name
puppet agent --test                                # 16. → creates certificate request, waits

C. On the server — sign the certificate, write the manifest:

docker exec -it puppet-server puppetserver ca list              # 17. pending request shown
docker exec -it puppet-server puppetserver ca sign --certname puppet-agent   # 18. sign it
docker exec -it puppet-server puppetserver ca list --all        # 19. verify (signed)

# 21-24. create and edit site.pp inside server
docker exec -it puppet-server bash
vi /etc/puppetlabs/code/environments/production/manifests/site.pp
# press i, then type:
file { '/tmp/hello.txt':
  ensure  => file,
  content => "Hello from Puppet!\n",
  mode    => '0644',
}
# save: Esc, then :wq

puppet parser validate /etc/puppetlabs/code/environments/production/manifests/site.pp  # 26. silent = valid
exit

D. Run the agent → verify:

docker exec -it puppet-agent puppet agent --test                # 28. applies the catalog
docker exec -it puppet-agent cat /tmp/hello.txt                 # → Hello from Puppet!
docker exec -it puppet-agent cat /var/lib/puppet/...            # (optional) check state
One-line story to remember the order: pull both images → run server (port 8140) → run agent → set server IP + certname in agent → agent --test (CSR) → ca list → ca sign → write site.pp on server → validate → agent --test again → check the file.
Troubleshooting: connection refused → is server container up + port 8140 (docker ps, docker logs puppet-server); SSL error → wait a few min for server certs or docker restart puppet-server; wrong server IP → puppet config print server inside agent; start over → docker rm -f puppet-server puppet-agent then re-create.

CHEATLast-Minute Cheat Sheet

Definitions in one line (memorize word-to-word)

  • Configuration Management: practice of handling changes systematically so a system maintains integrity over time.
  • Puppet: open-source configuration management tool, pull-based, enables IaC with a declarative language.
  • Manifest: .pp file in Puppet DSL describing desired state.
  • Module: self-contained bundle of manifests + files + templates (reusable).
  • Template: code + data → rendered final document (ERB, dynamic content).
  • File (server store): static content downloaded by clients.
  • Facter: gathers system facts (hardware, OS, network) from nodes.
  • Catalog: compiled document describing desired state of one node, made by master from manifests.
  • Certificate Authority: master component that signs agent certificates for SSL trust.
  • Idempotency: same config applied many times = same result, no side effects.
  • Push: server initiates (Ansible, SaltStack). Pull: node initiates (Puppet, Chef).
  • Agent: requests catalogs, applies config, reports back, gathers facts.
  • Master: stores manifests/modules, compiles catalogs, manages certificates, serves files/templates.

Port, paths & numbers (frequently asked)

  • Port 8140 — Puppet master listens; all master-agent communication is SSL on 8140.
  • Production code dir: /etc/puppetlabs/code/environments/production/ (manifests/ + modules/)
  • puppet.conf: Linux /etc/puppetlabs/puppet/puppet.conf · Windows C:\ProgramData\PuppetLabs\puppet\etc\puppet.conf
  • Windows paths: SSL certs C:\ProgramData\PuppetLabs\puppet\ssl\ · binaries C:\Program Files\Puppet Labs\Puppet\bin\
  • Java: Puppet Server needs openjdk-17-jdk; reduce heap with Xms512m/Xmx512m on small VMs.
  • Master runs only on Linux; agent runs on Linux, Windows, macOS.
  • runinterval — how often agent checks in (e.g. 30m / 1h).

Order of the master-agent story (memorize the 8 steps)

  1. Install master (Linux) + agent
  2. Configure puppet.conf on both (certname, server, environment)
  3. Map hostnames in /etc/hosts; open port 8140
  4. Start puppetserver; verify with ss -tlnp | grep 8140
  5. puppet agent --test on agent → sends CSR
  6. puppetserver ca list → ca sign --certname … on master
  7. puppet agent --test again → fetches and applies catalog
  8. Verify the result (file created / service running / web page)

Most-likely "what is" questions — answer in 2 lines each

  • What is site.pp? The entry-point manifest in production environment; contains node definitions and include statements applied to agents.
  • What is a catalog? Compiled desired-state document for one node; master compiles it from manifests+facts; agent applies it.
  • What is Facter? Inventory tool that collects facts (OS, IP, memory) sent with each agent run so manifests can adapt.
  • What is idempotency? Applying the same manifest repeatedly gives the same result — 1st run changes, later runs do nothing.
  • What is the difference between manifest and module? Manifest = single .pp code file; module = organized bundle of manifests+files+templates+metadata, reusable.
  • What is the difference between puppet apply and puppet agent? apply = local, masterless, one manifest; agent = gets catalog from master over SSL (port 8140).
  • Why certificate signing? Master and agent must trust each other (SSL); master's CA signs the agent's CSR before serving any catalog.
  • What is node classification? Deciding which configuration/classes apply to which node (node definitions in site.pp).
  • What is an environment in Puppet? Isolated code branch like production/development at /etc/puppetlabs/code/environments/.
  • What is Puppet Forge? Public repository of community-made modules you can reuse.
